TicketRush: consistencia con Redis y procesamiento concurrente con Worker Threads

En este taller deberá diseñar e implementar un sistema distribuido para la reserva de 20 cupos de un evento.

El sistema recibirá múltiples solicitudes concurrentes, será desplegado con varias réplicas y deberá garantizar que nunca se aprueben más reservas que los cupos disponibles.

Además, cada reserva aprobada deberá ejecutar una tarea de procesamiento CPU-bound, por ejemplo generación de un código de validación, comprobante, firma simulada o cálculo intensivo.

Durante el taller se analizarán dos problemas diferentes:

Consistencia distribuida: varios Pods intentan modificar el mismo recurso lógico.

Procesamiento concurrente: varias tareas CPU-bound necesitan ejecutarse sin bloquear innecesariamente el Main Thread.

Para resolver y evaluar estos problemas se utilizarán Node.js, Worker Threads, Redis, Kubernetes y Grafana k6.

El objetivo no es únicamente lograr que la aplicación funcione. Debe demostrar mediante experimentos qué problema aparece, cómo lo solucionó y qué efecto produjo cada decisión.

Objetivos
Al finalizar el taller, el estudiante deberá ser capaz de:

Identificar una condición de concurrencia sobre un recurso compartido.
Explicar por qué un Mutex local no coordina varios procesos o Pods.
Utilizar Redis como mecanismo de coordinación o almacenamiento de estado compartido.
Implementar tareas CPU-bound mediante Worker Threads.
Limitar la cantidad de Workers simultáneos y evaluar experimentalmente diferentes configuraciones.
Utilizar k6 para generar concurrencia y obtener evidencia cuantitativa del comportamiento del sistema.

su propio estado

Parte 5. Incorporar procesamiento CPU-bound
Cada reserva aprobada deberá generar posteriormente algún trabajo CPU-bound.

Ejemplos posibles:

hash repetitivo
firma simulada
procesamiento matemático
generación de comprobante
La tarea debe durar lo suficiente para observar experimentalmente su impacto.

Implemente dos versiones:

Modo MAIN
La tarea CPU-bound se ejecuta en el Main Thread.

Modo WORKER
La misma tarea se ejecuta mediante Worker Thread.
No disminuya artificialmente el trabajo en la segunda versión. El cálculo debe ser equivalente.

Preguntas de análisis
1. Con una sola réplica, un Mutex puede proteger correctamente una sección crítica. ¿Por qué esa misma solución deja de ser suficiente cuando existen tres Pods? Explique qué memoria y qué mecanismo de sincronización posee cada proceso.

2. Su sistema recibe 100 solicitudes concurrentes para 20 cupos. ¿Qué evidencia permite afirmar que su solución con Redis mantiene consistencia y no simplemente que las solicitudes respondieron correctamente?

3. ¿Por qué Worker Threads no soluciona la consistencia entre Pods y por qué Redis tampoco soluciona por sí solo el bloqueo del Main Thread?

4. Analizando sus resultados con 1, 2, 4 y 8 Workers, ¿qué configuración obtuvo el mejor equilibrio en su equipo? Sustente su respuesta con requests/s, p95, máximo, errores y tiempo total.

5. Una reserva fue confirmada y Redis descontó correctamente el cupo, pero el cliente no recibió la respuesta y vuelve a enviar exactamente la misma solicitud. ¿Qué problema puede producirse y cómo modificaría el sistema para evitarlo?
